<p>多个号挤一条线的时候，最难受的不是慢，而是出问题找不到人。三个号同时报错，你得一个个试，试到最后才发现是线路在抖，而不是某个号被封。这篇设计一次对照实验，专门量「定位要多久」这件事，而不是只看成功率。</p>
<h2>一、这次要验证的是「能不能一眼定位」</h2>
<p>常规评测只看请求成功率，但成功率高的配置也可能让你天天猜谜。真正影响日常效率的是归因速度：一个号出异常，你能不能在五分钟内判断是号的问题、环境的问题，还是这条线的问题。</p>
<h3>把「一眼找到」拆成可测的量</h3>
<p>拆成三项：故障半径（一次异常波及几个号）、定位耗时（从发现到给出结论的分钟数）、重复排查次数（同一个根因被反复怀疑几次）。三项都能从日志里读出来，不靠感觉。</p>
<h3>为什么不用「平均延迟」当主指标</h3>
<p>延迟差异在几十毫秒量级，日常使用根本感知不到，拿它当结论容易误导。归因类指标差异往往是数量级的，更容易得出结论。</p>
<h2>二、怎么分组，只改一个变量</h2>
<p>两组对照：甲组三个号共用一条静态出口，各自环境分开；乙组三个号各占一条静态出口，环境同样分开。两组的环境配置完全一致，唯一差别是出口是否共用。</p>

<h3>为什么环境都分开</h3>
<p>如果甲组环境也共用，就变成了两个变量同时变，最后说不清是出口还是环境造成的差异。环境统一按最优配置来，把出口单独拎出来测。</p>
<h3>两组要同时跑</h3>
<p>错开时间跑没意义——平台侧的状态、网络状况都在变。两组同一天同一时段启动，日志时间戳对齐，才有可比性。</p>
<h2>三、观测指标怎么记</h2>
<p>四个字段必须逐条落日志：时间戳、账号编号、出口 IP、状态码。另外加一列「备注」，人工填当时的主观判断。事后回看时，主观判断和日志往往对不上，这个对不上的地方就是定位耗时的来源。</p>
<h3>定位耗时怎么算</h3>
<p>从第一条报错日志的时间，到你在台账里写下根因的时间，两者相减。别事后补记，补记的数字一定是美化过的。用秒表或者直接看聊天记录时间戳。</p>
<h3>故障半径怎么算</h3>
<p>一次异常事件里，受影响的不同账号数量。甲组共用出口，一条线抖三个号一起抖，半径就是 3；乙组某个号自己出问题，半径是 1。</p>

<h3>成功率为什么也会差</h3>
<p>共用出口时，一个号的高频请求会把整条线的配额拉紧，其他号跟着受影响。静态住宅出口的带宽与并发本来就有限，三个号同时跑，触发限流的概率自然上升。</p>
<h2>五、日志怎么记，结论怎么固化</h2>
<p>日志的价值不在于全，而在于能快速筛。三个字段就能支撑大部分定位：出口 IP、账号编号、状态码。再多加一个时间戳，就够画出时间线。</p>
<h3>一行一条，别写多行</h3>
<p>多行日志没法直接筛，出问题时只能肉眼翻。一行一条 JSON，字段名用英文短词，导出到表格后按出口 IP 分组，一眼就能看出是单号问题还是整条线的问题。</p>
<h3>给每个环境包编号</h3>
<p>环境目录、账号、线路三者用同一套编号互相引用。出问题时先看编号对不对，编号错位说明是人为配错，不用往线路方向查。</p>
<h3>把结论固化成三条规则</h3>
<p>实验做完，结论要变成一条能执行的规则，否则过两个月又回到老样子。这次的结论很直接：出口与账号一对一绑定，绑定关系写进台账，不随临时需求调整。</p>
<p>一是新号上线必须分配独立出口，不允许「先共用着」；二是出口变更必须走登记，登记内容包括时间、原因、操作人；三是异常排查先看台账绑定关系，再看线路状态。</p>
<h3>什么时候该重做实验</h3>
<p>换地区、换服务商、账号量翻倍、任务类型从对话改成批量文档处理，这四种情况都值得再跑一次七天。旧结论一般撑不过一个季度。</p>
<h2>常见问答</h2>
<h3>只有三个号，做对照实验值得吗？</h3>
<p>答：值得，但可以缩短到三天。三个号规模小，重点看故障半径和定位耗时这两项，成功率参考意义不大。</p>
<h3>静态住宅出口为什么比动态的更适合这个实验？</h3>
<p>答：静态出口的 IP 不变，排除掉「换 IP 导致的变量」，能干净地比较共用与独占的差别。动态出口做对照，需要额外控制轮换频率。</p>
<h3>定位耗时的主观成分太大怎么办？</h3>
<p>答：用可观测的锚点代替感觉，比如「第一条报错日志时间」到「台账写下根因时间」。两个时间都来自系统记录，比回忆可靠。</p>
<h3>共用一条线但限制并发，能不能达到类似效果？</h3>
<p>答：能缓解一部分，但故障半径依然是三个。限并发解决的是相互挤占，不解决「一起被牵连」的问题。</p>
